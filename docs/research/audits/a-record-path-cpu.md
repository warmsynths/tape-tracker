# Audit A: record-path-and-latency.md, cpu-ram-budget.md, readiness-matrix.md against v1.0.0

Read-only audit of `/home/user/tape-tracker` (v1.0.0 plus our additions). Nothing was built or run. Everything below is from reading source. Where a conclusion depends on reading the update order of audio nodes, I say so and rate my own confidence.

## How to read this

- Status: VERIFIED (true in v1.0.0), DIFFERS (wrong or changed in v1.0.0, correct statement given), NOT FOUND (searched, not in v1.0.0), ESTIMATE (arithmetic, guess or not checkable without hardware).
- "Cite" = the file:line the document gave. Evidence lines are in the current tree. Our additions shifted some files: `core/AudioEngine/mtAudioEngine.cpp` is +13 lines after about line 150 (v1.0.0 `audioEngine::update` is at 273, now 286), `core/source/Recorder.cpp` is +5 to +6 lines. The two research documents use v1.0.0 numbers for `mtAudioEngine.cpp` (273-277 is right for v1.0.0) but wrong numbers for several other files (listed in "Citation drift").
- Whole files that the documents cite do not exist in v1.0.0 or in this tree: `docs/memory_map.md` and `UPCOMING.md` (a stray copy of `UPCOMING.md` sits in `.claude/worktrees/agent-a4a17d3aa44de60d7/`, which is not part of v1.0.0). Every claim that rests only on those two files is marked DIFFERS or NOT FOUND below.
- I could not re-link the firmware, so the SDRAM, flash and RAM figures come from `docs/build-notes.md` (our own build of v1.0.0) and I did not re-measure them.

## Things this document got wrong or missed

1. **The latency is probably two blocks (5.8 ms) larger than stated, and the alignment constant with it.** Two out-of-order declarations (`AudioOutput.h:44-46`: `outputStream` before `finalMixer`; `AudioInput.h:30-40`: record queues before `stereoToMono`) each add a one-block delay in v1.0.0. The research assumed the update order adds none, and relied on a `hasLaterSource` mechanism that is not in v1.0.0 (R20, R21). Effect: monitor path 3 to 4 blocks, loop-output-to-record-queue 4 to 5 blocks (R39), not 2 to 3. This changes the slice-2 compensation constant and the pre-roll sizing. Medium-high confidence from static reading; it is exactly what ticket 13 (cable loopback) will confirm or refute. Cheap extra check: a debug build that logs the order of `AudioStream::first_update` nodes.
2. **The recorder freeze does not affect our four loops.** `AudioPlayLoops` is not a `playerEngine`. The guard only matters for pad hits and instrument notes. The matrix lists "stop the recorder freezing voices" as a prerequisite for rows 1 and 4; it is a prerequisite for feature 16 only (C3, M4).
3. **Memory baselines came from the wrong build.** Free SDRAM is 1.13 MiB, flash about 170 KB free, internal RAM about 127 KB free on v1.0.0, not 1.04 MiB, 144 KB and 80.6 KB. `docs/memory_map.md`, which both documents cite, does not exist here (C28, C29).
4. **USB audio and USB interrupt claims are wrong for the Original.** USB is interrupt priority 7, and USB audio streaming is IMX-only (R24, C6, C40).
5. **v1.0.0 already runs the codec's DAP in the output path** (`SSS_CTRL = 0x0070`). This may add its own processing delay not counted anywhere, and it also means the DAP-mixer hardware monitor idea is closer than the doc thought (R4, R36). Datasheet needed.
6. **MK66 voice chain is lighter than described** (one RMS, no pan amplifiers) and **the freeze/streaming/instrument hazards were written for instrument voices, not for our loop player** (C14, C36, C37). The CPU table is for a design we did not build.
7. **Citation drift.** Many file:line cites point at the unreleased main. Wrong for v1.0.0: `Input.cpp:76-79`, `AudioStream.cpp:342-358`, `Recorder.cpp` (all), `fSampleRec.cpp` (all), `Tracker.cpp` (about 9 lines too high), `mtTest.cpp`, `mtStructs.h` (a few lines), `mk66fx1m0.ld:4-8`, `developer_guide.md:43, 259`, `AudioVoice.cpp:30-39`. The content behind most of them is real. Right for v1.0.0: `mtAudioEngine.cpp:273-277`, `input_i2s.cpp`, `output_i2s.cpp`, `interruptsConfig.h`, `record_queue.*`, `config.h`.
8. **Streaming condition was mis-stated** (C36): it is size AND a streamable play mode, and only on instrument load from SD.
9. **Record queue memory is the shared block pool, not a private 2.6 KB** (C34), which matters if the queue ever backs up.
10. **The "no pre-roll" and "no sample-accurate start" statements are right** (R28, R30), and a first-block hook already exists in our tree, but it measures the position when the block is copied, not when it was captured.

## Limits we declared that the code does not actually impose

- **"The recorder writes to the start of the pool and must be pointed elsewhere."** It writes where `setConfig` is told (`Recorder.cpp:14-33`). Only the stock screen passes the pool start. Our screen already passes its own regions.
- **"Four Parts must be 30 s."** The 30 s was a planning number. Code limits are: `SAMPLE_MEMORY_SIZE` 11.25 MiB and the regions our code picks (`kMaxLoopFrames` 24 s, `kRegionFrames` 26 s, `fFourTrack.cpp:28-33`). Nothing in the audio code stops other lengths.
- **"The Sample Editor and `.ptfx` machinery must be removed for RAM to fit."** The editor overlap is real but it is a layout choice (`EDIT_BUFF_OFFSET`, `mtStructs.h:85`), proportional to what is edited, and only occurs if someone edits. It only needs resolving if the editor stays reachable alongside Four-Track.
- **"Parts must be resident in RAM; streaming is a hazard."** v1.0.0 already has an SD streaming engine (`VoiceStreamManager`, 8 voices, 16,384-frame rings, about 371 ms, 743 ms pre-cache per `developer_guide.md:89`). It is tied to instruments and `playerEngine` voices, so `AudioPlayLoops` cannot use it as is, and a looping Part needs an instant wrap. I do not claim it fits our use; I claim it is a mechanism the documents wrote off by default rather than assessed.
- **"A separate 30 s staging buffer does not fit."** True for 1.13 MiB free, but the recorder can write straight into the final region, so no staging buffer is needed (this is what the code does).
- **"Recording freezes voice updates, so the guard has to go."** Not imposed on loop playback (C3).
- **"USB at priority 3 can disrupt audio."** Not imposed; USB is the lowest priority (R24).
- **"Latency is fixed at two 128-sample blocks."** The block size is a compile-time constant (`config.h:12-14`, "sync w config.inc" at `platforms/mk66/config/config.inc`), and `AudioStream.h:41-50` says it may be reduced for lower latency. Polyend warn that some parts hard-code 128, and I did not check them. So the latency floor is a choice of build, not physics. I am not recommending changing it.
- **"Monitor must go through the software chain."** The codec can switch its DAC source and has DAP mixer registers (R35, R36). Nothing in the code forces software monitoring; it is just what the stock recorder uses.
- **"Sample-accurate start needs a new interrupt-side mechanism."** Part of it exists (`setFirstBlockCallback`, R31); what is missing is arming the record queue from the audio side instead of the UI loop.

## Uncertainty, plainly

- I did not trace which interrupts `DISABLE_AUDIO_INTERRUPTS` masks, the `DMAMEM` placement, SDRAM bus width or caching.
- Hardware-only statements (codec delay, RX/TX phase, CPU percentages, SDRAM read cost) stay unverified. Nothing here has been measured on the device.
